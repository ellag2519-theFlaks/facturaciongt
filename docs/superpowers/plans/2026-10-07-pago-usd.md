# Pago de Facturas en Dólares — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a seller mark an invoice as paid in USD; the backend fetches the day's real exchange rate from a reused `exchange-service` microservice (consuming Banco de Guatemala's live SOAP service) and stores the GTQ amounts plus the converted USD total, blocking the invoice cleanly if the rate can't be fetched.

**Architecture:** `exchange-service` is copied verbatim from `Análisis II/Primer parcial/FinanzasGT` as a new, unmodified, independently-running Express microservice (port 3002). `facturacion-service` gains an HTTP client to it, called *before* the existing atomic SQLite transaction (which must stay fully synchronous), and the transaction's final step stores the already-fetched rate and the computed USD total alongside the existing GTQ fields. The frontend adds a currency selector and renders the USD figure when present — GTQ invoices are completely unaffected.

**Tech Stack:** Node.js + Express 5 (exchange-service, unchanged from FinanzasGT), `axios` (new dependency in `facturacion-service`), `better-sqlite3`, React 19. Python + Playwright for the one E2E scenario that depends on real internet connectivity.

**Spec:** `docs/superpowers/specs/2026-10-07-pago-usd-design.md`

## Global Constraints

- `exchange-service` is copied **unmodified** from `C:\Users\ellag\OneDrive\Escritorio\Universidad\8vo. Semestre\Analisis II\Primer parcial\FinanzasGT\exchange-service` — no logic changes, no new tests added to it. It already returns errors as `{ error: { code, message } }`, matching this project's convention exactly.
- `better-sqlite3`'s `db.transaction()` must stay fully synchronous — the exchange-rate HTTP call happens *before* `invoiceModel.createInvoiceWithItems` is invoked, never inside it.
- Products keep their base price in GTQ always. `subtotal`/`tax`/`total` (existing columns) are never recalculated or overwritten in dollars — they stay the GTQ source of truth.
- New invoice columns: `payment_currency TEXT NOT NULL DEFAULT 'GTQ' CHECK (payment_currency IN ('GTQ', 'USD'))`, `exchange_rate REAL` (nullable), `total_usd REAL` (nullable) — both null unless `payment_currency = 'USD'`.
- `total_usd = Math.round((total / exchange_rate) * 100) / 100` (`exchange_rate` is GTQ per 1 USD, matching Banguat's reference rate convention).
- New error code: `EXCHANGE_SERVICE_UNAVAILABLE` (502), same `{ error: { code, message } }` envelope as every other error in this backend — covers timeout, unreachable, and error-response cases from `exchange-service` alike (the seller doesn't need the technical distinction).
- Backend `node --test` suite stays network-free: `exchangeClient.js` reads `process.env.EXCHANGE_SERVICE_URL` fresh on every call (not through the frozen `env.js` singleton) specifically so tests can point it at an ephemeral local stub server without an import-ordering problem — this is a deliberate, intentional deviation from this codebase's usual "centralize config in `env.js`" convention, made for testability. Don't "fix" it back.
- `exchange-service`'s own `.gitignore` is not copied — the project root's `.gitignore` already ignores `node_modules/` and `.env` at any depth.

## Review Focus

- A GTQ invoice (the default, and every invoice created before this feature existed) must behave identically to today — including when `exchange-service` is completely unreachable, since a GTQ invoice must never call it — Task 4.
- Choosing USD when `exchange-service` is unreachable must leave the database exactly as it was before the request (no partial invoice, no stock decremented) — not just return an error — Task 4.
- The exchange rate used must be the one fetched *before* the transaction, not re-fetched or recomputed inside it, so a rate change mid-request can't produce an invoice whose stored `exchange_rate` doesn't match its own `total_usd` — Task 4.
- Running `facturacion-service/src/database/schema.js` a second time (e.g. every server restart) against a database that already has the new columns must not throw — Task 2.
- The currency selector's value must actually reach the backend as `payment_currency` in the `POST /api/invoices` body — a frontend-only toggle that doesn't wire through would look correct in the UI and silently always bill in GTQ. Frontend tasks in this project are build-verified only (no component-level test framework); this one is proven by Task 7's E2E scenario, which selects Dólares in the real UI and asserts a real USD amount comes back — not by Task 5 itself.

- Produces: `startStubExchangeService({ rate = 7.8, date = '2026-10-07', status = 200 } = {})` (named export, async, `test/helpers/stubExchangeService.js`) — starts a local `http` server on an OS-assigned ephemeral port serving `{ rate, date }` as JSON on any request when `status` is 200, or a generic JSON error body when `status` is anything else; sets `process.env.EXCHANGE_SERVICE_URL` to point at it; returns `{ close: () => Promise<void> }`. Other test files reuse this directly — don't re-implement a stub server per file.

- [ ] **Step 1: Write the stub helper**

```js
// facturacion-service/test/helpers/stubExchangeService.js
import http from 'node:http'

export async function startStubExchangeService({ rate = 7.8, date = '2026-10-07', status = 200 } = {}) {
  const server = http.createServer((req, res) => {
    res.writeHead(status, { 'Content-Type': 'application/json' })
    res.end(status === 200
      ? JSON.stringify({ rate, date })
      : JSON.stringify({ error: { code: 'STUB_ERROR', message: 'stub error' } }))
  })
  await new Promise((resolve) => server.listen(0, resolve))
  process.env.EXCHANGE_SERVICE_URL = `http://localhost:${server.address().port}`
  return { close: () => new Promise((resolve) => server.close(resolve)) }
}
```
